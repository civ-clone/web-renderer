# Review: src/js/Engine/DataTransferClient.ts (origin/main 18f28b0)

## Area health

The patch machinery is in good shape. Builders are lazy, there is one entry per object per flush (`#queuedTiles`/`#queued`), held actions go as refs, and the stand-ins (`unitWithoutActions`, `playerWithoutActions`, `withoutAvailable`) work: each consumer either reads through to the real object or serialises additional data from the real object. I found no consumer that receives a stand-in where it needs the real object. `#dataFilter` also holds for every payload that is not a city investigation.

The weak spots are the paths that leave the normal "one action, one flush, one ack" flow:
- **Prompts to the player.** Only one `chooseFromList` can be pending. A second one silently disposes the first.
- **Talks outside an action.** Talks at turn start, or talks a computer player opens, skip `#sendPlayerState`, and `EndTurn` does not wait for them.
- **Errors.** A throw in an action or in a patch builder is not isolated. It ends the turn silently, or leaves the queue holding a builder that throws on every flush.

Holds are released on all normal paths: `#holdingFlushes` (in a `finally`), `#cityNews` (a microtask, cleared before sending), and `#heldHalts`/`#heldNotifications` (`#handOver`). The exceptions are the catch path in `takeTurn` and the timer in `takeTurn`, below.

- #449: splitting DataTransferClient.ts into modules. The in-code TODOs (hidden actions, `handleNegotiation` duplicated in simple-ai-client) are listed under "Source-level TODO hotspots" in docs/known-issues-and-rewrite-notes.md.
- #315: the cost of `City.yields()`. Every `#sendCity` and `serialiseTile` pays it.

- #416: late-game notifications that overflow onto the game menu.

## Engine

- civ1-science `Rules/City/captured.ts`: `steal-advance` is an async Effect, and nothing awaits it (`City.capture` is synchronous), so its prompt runs detached from the capture action. This is the root of scenario (a) in the first finding.
- civ1-diplomacy `Rules/Proposal/resolved.ts` `give()`: moves gold without an event, so no client can tell a treasury changed.
- core-diplomacy/library-diplomacy: a `Negotiation` is registered only once it terminates, so `mayNegotiate`/`lastNegotiated` allow a second talk between the same pair while one is still open.
- simple-ai-client `lib/Diplomacy/negotiate.ts`: has the same unbounded loop as `handleNegotiation`.
- core-player-world `PlayerWorld.entries()`/`filter()` copy the whole known world on every call. `handleAction` (`filter` by id, per move or tile change) and the visibility handler (`entries().indexOf`, per newly seen tile) call them.

## Simplifications

- `#sender`/`#receiver` (lines 377-378, 408-409) are stored and never read. Game.ts and about 24 test call sites pass closures for nothing.
- The `Retryable` branch in `player:visibility-changed` (713-736) is dead: `PlayerWorld.register` adds the tile before it runs `VisibilityChanged`, so `getByTile` is never null. Retryable.ts can go too, and its rejected promise was never handled.
- `handleNegotiation`/`talkToPlayersMet` duplicate simple-ai-client's `handleNegotiation` (in-code TODO). Exporting one with a "chooser" hook would also fix the unbounded loop in one place.
- `playerWorld.entries().indexOf(playerTile)` (726, 742) copies and scans the known world for each newly seen tile. A tile that was just registered is always the last entry.
- `handleAction` builds `player.actions()` (every unit's and city's rules) before dispatching, even for `ReassignWorkers`, which never reads them. Build it after the `ReassignWorkers` branch.

## Coverage gaps

- tests/engine/choosePrompts.ts (new): a capture that triggers the steal prompt, then talks in the same action. Both answers must land, and the advance must be granted.
- tests/engine/turnHandover.ts: send `EndTurn` while the turn-start talks are pending, and send a second `EndTurn` after `turnEnded`. Expect `turnEnded` and `turnStarted` to alternate, and `#talks` to settle.
- tests/engine/oneFlushPerAction.ts: an action whose `perform` throws (stub a unit action). Expect `actionHandled`, a flush, and the listener still attached. Add a patch builder that throws once, then check that the next flush succeeds.
- tests/engine/diplomacy.ts: tribute accepted in turn-start talks. Expect a `PlayerTreasury` patch with the new value.
- tests/engine/diplomats.ts: investigating a rival city. Expect no `available` key on its `CityBuild`.
- tests/engine/cheats.ts: GrantAdvance of the advance being researched. Expect `ChooseResearch` in the `mandatoryActions` patch. Also cover ModifyUnit.
- tests/engine/transportRequests.ts: a request handler that throws must still reply, so the next request on the channel resolves.

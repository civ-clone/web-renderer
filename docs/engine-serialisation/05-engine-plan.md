# 05 — Engine Implementation Plan

Eight stages. Each lands as a set of published patch releases and leaves the
engine working. Read [`04-package-workflow.md`](./04-package-workflow.md) first —
every stage assumes its tooling and its version strategy.

The renderer plan follows separately, once this is agreed.

## Context

Multiplayer is a genuine target, which changes the ordering. Stable identity and
determinism stop being save/load conveniences and become prerequisites — matching
`web-renderer-rewrite`'s DEC-009, which said no save/load ships until the stable
ID strategy is confirmed.

Here that strategy is a restored id counter plus deterministic creation order
rather than a parallel stable ID; the reasoning, and the case against, is in
[`03-save-format.md`](./03-save-format.md) §"On stable IDs".

## Decisions carried forward from `web-renderer-rewrite`

That effort is parked, but its ADRs were reasoned and several were reached
independently here. Explicitly:

| Decision | Status |

| DEC-003 Normalised state, ID-only references | **Carried.** Independently arrived at. |

## Stage 0 — Foundations

**No package changes.** Build the things that make the other stages verifiable.

### Deliverables

1. **`tools/civ`** — `audit`, `clone`, `sync`, `watch`, `publish`, `check-dts`.
   Specified in [`04-package-workflow.md`](./04-package-workflow.md).
2. **`tools/packages.json`** — generated by `civ audit --write`, committed.
3. **All 62 repos cloned** — `civ clone --stage 1`.
4. **Conformance suite** — `web-renderer/tests/engine/`. Drives the engine
   headlessly through a seeded game; asserts entity counts by type, registry
   sizes, turn advancement, and a state checksum at turns 1, 10 and 50.
5. **Baseline recorded** — run it and commit the checksums as fixtures.

### On the checksum

It must be computed from **state, not the DTO** — sorted entity ids, types, and
`toState()`-eligible fields — otherwise it changes whenever a derived value's
`Yield` object is reallocated, which is every call.

Before Stage 4 there is no `toState()`, so Stage 0's checksum is a deliberately
narrow subset: entity id, type, and a hand-listed set of scalar fields per type.
Widen it in Stage 4. Say so in the fixture file, or the next person will assume
it is complete.

### Acceptance

- [x] `civ audit` reproduces the table in [`04-package-workflow.md`](./04-package-workflow.md) —
      325 installed, 22 from GitHub, 62 packages / 282 declarations / 12 waves,
      17 `registerRules.ts`, 19 `Math.random`, one cycle group
- [x] `civ clone --stage 1` leaves 62 clean checkouts
- [x] `civ sync core-city` round-trips an edit into a `web-renderer` build
- [x] Conformance suite runs in under 60s (11s) and passes twice with the same seed
- [x] Checksum fixtures committed — `tests/engine/fixtures/baseline.json`

### What the suite actually asserts

`npm run test:conformance` drives a seeded four-player game on a 60×40 world to
turn 50 and records two independent things at turns 1, 10 and 50:

- **`checksums`** — engine state: registry sizes, a terrain hash, and per-entity
  id/type/scalars for every player, city and unit. The narrow Stage 0 subset.
- **`snapshots.*.dto`** — the object count, byte size and hash of what
  `toPlainObject()` emits for every player, city and unit. That is the
  renderer's actual transport payload.

The DTO digest is **outside** the checksum on purpose. "The engine behaves
identically" and "the wire format is unchanged" are different questions, and
Stage 1 turns out to answer them differently — see Stage 1's findings below.

Determinism comes from seeding `Math.random` globally at boot, which works
because there is one game per process. Stage 2 replaces it with an injected
`Rng`; Stage 3 makes the global impossible.

## Stage 1 — `#private` → `private`

**62 packages, 280 field declarations, 12 waves.** Mechanical. This is also the
rehearsal for the tooling — if the workflow is wrong, find out here where every
change is trivially reviewable.

### The change

```ts
// before
export class City extends DataObject {
  #name: string;
  #player: Player;

  name(): string { return this.#name; }
}

// after
export class City extends DataObject {
  private _name: string;
  private _player: Player;

  name(): string { return this._name; }
}
```

### Rules

- **`_` prefix, always.** Distinguishes state from public API at a glance and
  keeps `Object.keys` output greppable.
- **`private`, not `protected`** unless a subclass already reaches the field.
  `Unit extends Buildable`, `CityImprovement extends Buildable`,
  `PlayerTile` overrides `addKey` — check each.
- **No behavioural change whatsoever.** No renames beyond the prefix, no
  reordering, no cleanup. Anything else goes in a separate commit.
- **Static fields and module-level `#` are out of scope.** Only instance fields.

### Codemod

```
tools/codemod/private-fields.ts
```

Use `ts-morph`. For each source file: find `PropertyDeclaration`s with a
`PrivateIdentifier` name, rename `#x` → `_x`, add the `private` modifier, and let
ts-morph update every `this.#x` reference. Then run the package's
`prettier:format` and `ts:compile`.

Manual review is still required per package — 280 declarations is small enough to
read. Watch for:

- `#x in obj` brand checks (the ergonomic private-field check). **None exist**
  today; if the codemod finds one it must be rewritten by hand.
- Getter/setter pairs where a `_x` name would collide with an existing member.
- `Object.defineProperty(this, ...)` interaction in `PlayerTile` — that code
  defines *public* accessors and is unaffected, but check it.

### Per-package procedure

```
civ sync <pkg>                    # baseline into node_modules
node tools/codemod/private-fields.ts ~/Code/civ-clone/<pkg>
cd ~/Code/civ-clone/<pkg> && npm run ts:compile && npm test
git diff                          # read it; 280 total across 62 packages
git commit -am "refactor: use TypeScript private instead of #private fields"
civ sync <pkg> && cd web-renderer && npm run build:dev   # spot check
```

Then per wave, `civ publish --wave N` and the wave gates from
[`04-package-workflow.md`](./04-package-workflow.md).

### What it cost, beyond the codemod

Six things needed a decision rather than a rename. They are recorded here
because each is a place a future reader will otherwise assume the mechanical
rule was applied and wonder why it was not.

**1. Shadowed fields cannot both be `private`.** Two `#private` fields of the
same name in one inheritance chain are separate slots and perfectly legal.
Two `private _x` are TS2415. Three chains had this:

| Chain | Resolution |
| ----- | ---------- |
| `core-diplomacy` `Declaration` over `Interaction` (`#turn`) | Base is `protected _turn`; the shadow is gone. Exactly behaviour-preserving — `Interaction` reads `_turn` only in its constructor, before `Declaration` can assign. |
| `core-civ-client` `Client` and `simple-ai-client` `SimpleAIClient` over `core-client` `Client` (`#randomNumberGenerator`) | Base is `protected _randomNumberGenerator`; both derived classes forward their generator to `super` instead of keeping a copy. Every construction site uses the default `() => Math.random()`, so nothing changes today. |

`civ collisions` finds these from source, which matters because the compiler
cannot: with a cross-package chain the error only appears once the **base**
package has published.

**2. Mixins cannot have private members at all.** `core-unit-transport`'s
`Transport` is `(Base: typeof Unit) => class Transport extends Base {…}`. TS4094
refuses to emit declarations for an exported class expression with private
members, so its two fields take the `_` prefix and no modifier. They were
already in the emitted `.d.ts` as `'__#30@#ruleRegistry'`, so this makes them
legible rather than newly public. `_ruleRegistry` also had to become
`_transportRuleRegistry`: a public member cannot shadow `Unit`'s `private
_ruleRegistry`, and the two were always separate slots — `Unit` takes an
injected registry, the mixin always used the singleton.

The codemod handles this: it skips the accessibility modifier inside a
`ClassExpression`. It also had to be taught to look inside class expressions at
all — `getClasses()` returns declarations only, and this mixin was silently
skipped on the first pass.

**3. `toPlainObject` now emits more.** `Unit.busy` returns a `Rule`, which is
not a `DataObject`, so `toPlainObject` walks it through its plain-object branch.
That branch used to see nothing (every field was `#private`) and emitted `{}`.
It now emits `{_enabled, _priority, _criteria}`. The payload grows by ~0.1% —
1.1 KB at turn 10, 8.9 KB at turn 50 — and truthiness is unchanged, so the
renderer behaves identically. It is the one wire-format change in the stage,
it is confined to that one site, and the DTO digest in the conformance fixture
is what found it.

This is worth fixing properly rather than tolerating, and Stage 4 is the place:
`Unit.busy` should serialise as a rule identity, not as the rule object.

**4. Four packages could never compile.** `base-goody-hut-advance`,
`base-goody-hut-city`, `core-unit-improvement` and `core-world-path` set
`lib: es2019`, and `core-data-object`'s `DataObject.ts` uses `BigInt`. Because
node resolution reaches the `.ts` rather than the compiled `.js`, they
type-check it, and it is TS2583. `core-engine` had the same shape for a
different reason: no `@types/node`, so `console` was unresolvable.

Nobody noticed because `tsc --build` skips when its outputs are newer than its
inputs, so a stale success looked like a real one. **Always pass `--force`
when the point of the compile is to prove something.** Each is fixed in its own
`build:` commit ahead of the refactor.

**5. `core-strategy`'s suite is flaky.** `StrategyRegistry.attempt` breaks
priority ties with `Math.floor(Math.random() * 3 - 1)` and
`tests/StrategyRegistry.test.ts` assumes an order — three failures in eight runs
on an unmodified tree. Not this stage's to fix; Stage 2 makes it deterministic,
though still arbitrary. The real fix is for the test to stop assuming.

**6. One published version is missing from the registry.**
`base-unit-action-sleep`'s lockfile pins
`@civ-clone/base-unit-action-build-railroad@0.1.0`, which is not on npm — only
`0.1.2` and `0.1.3` are. `npm ci` cannot install that package at all. This is
the failure mode `04-package-workflow.md` §Rollback warns about, already in the
tree.

### Before publishing

Publishing has not happened; `npm whoami` reports no login. Two things must be
true first, and `tools/verify-stage1.js` checks both:

- No package still holds compiled output built from the old source. A package
  whose `ts:compile` failed got its `.ts` committed beside a stale `.js`, which
  would ship a package whose entrypoint still uses WeakMap private fields.
- `civ collisions` is clean.

Then `civ publish --wave N --dry-run` per wave. Note that `civ publish` asks the
remote for the default branch rather than assuming `main`: every civ-clone repo
is on `master`.

The 22 GitHub-resolved packages have no npm release — for those, pushing the
branch *is* the publish, and `civ publish` skips `npm publish` accordingly.

## Stage 2 — Deterministic RNG

Nineteen packages call `Math.random()`. None captures it at module scope
(verified in [`01-constraints.md`](./01-constraints.md) §7 — note `grep -R`, not
`-r`, because pnpm symlinks the tree).

A global `Math.random` override at worker boot would work for a single game and
needs no engine change. **It does not survive Stage 3**: two `Game`s in one
process would share the overridden global and interleave draws, diverging both.
So the RNG must be injected.

### The change

`core-rule` or a new `core-random` gains:

```ts
export interface Rng {
  (): number;
  seed(): number;
  calls(): number;
  restore(seed: number, calls: number): void;
}

export const createRng = (seed: number): Rng => { /* mulberry32 + call count */ };
export const instance: Rng = createRng(Date.now());
```

Then, following the existing idiom — injected with a singleton default, exactly
as `Spaceship` already does with `#randomNumberGenerator`:

```ts
constructor(/* … */, rng: Rng = rngInstance) {
  this._rng = rng;
}
```

Every `Math.random()` becomes `this._rng()`. In rule factories, `getRules(…, rng
= rngInstance)`.

### Call sites

`base-goody-hut-advance`, `base-goody-hut-unit`, `base-unit-action-attack`,
`civ1-city-improvement`, `civ1-goody-hut`, `civ1-science`, `civ1-spaceship`,
`civ1-unit`, `civ1-world`, `core-civ-client`, `core-civilization`, `core-client`,
`core-spaceship`, `core-strategy`, `core-terrain-feature`, `core-trade-rate`,
`simple-ai-client`, `simple-world-generator`. Plus `civ1-asset-extractor`, which
is renderer-side and can be skipped.

`simple-world-generator/BaseGenerator.ts` also has a hardcoded
`Math.floor(height * width * Math.random())` for the island seed tile, separate
from its already-injectable `randomNumberGenerator`. Route both through the
injected `Rng`.

### `calls()` matters

The count of draws taken must be tracked and persisted, so a load *resumes* the
stream rather than restarting it. Restarting would make a save/load cycle change
the next combat result — the exact bug that makes replay testing untrustworthy.

### Acceptance

- [ ] `grep -Rn "Math.random" ~/Code/civ-clone/*/` finds nothing outside
      `core-random` and the asset extractor
- [ ] Two runs with the same seed produce identical checksums at turns 1/10/50
- [ ] Two `Rng` instances with different seeds do not interfere
- [ ] `restore(seed, calls)` reproduces the stream from mid-game

## Stage 3 — The `Game` context

**The riskiest stage.** Also the one that unlocks multiplayer, test isolation and
load-into-fresh-context.

**Switch to the workspace overlay before starting this** — see
[`04-package-workflow.md`](./04-package-workflow.md) §"When to switch". This is
the one stage where ~45 packages must change coherently and cannot be
meaningfully tested until they all have; copy-sync means re-syncing dozens per
attempt. Note the pnpm 10+ `linkWorkspacePackages: false` default recorded there,
which silently sends pnpm to the registry instead of linking.

### The change

```ts
export class Game {
  readonly rules = new RuleRegistry();
  readonly cities = new CityRegistry();
  readonly units = new UnitRegistry();
  readonly players = new PlayerRegistry();
  readonly rng: Rng;
  readonly turn = new Turn();
  readonly year = new Year();
  // …one per registry, 31 entity + 12 constructor
}
```

The dependency injection already exists — every class and every rule factory
takes its registries as parameters with singleton defaults
([`01-constraints.md`](./01-constraints.md) §3). What is missing is something to
pass.

The binding point is plugin registration, in 17 `registerRules.ts` files:

```ts
// today — no arguments, so the singleton defaults win
ruleRegistryInstance.register(...cityCreated(), ...cityGrow());

// after
export const register = (game: Game): void =>
  game.rules.register(
    ...cityCreated(game.cities, game.rules),
    ...cityGrow(game.cities)
  );
```

### Migration

Keep the singleton exports throughout, as a default `Game`:

```ts
export const defaultGame = new Game();
export const instance = defaultGame.cities;   // unchanged for every consumer
```

Nothing outside breaks. Packages migrate to `register(game)` one at a time, and
the singletons are deleted only once every caller has moved — which may be after
this plan ends. That is fine.

### Why this is medium–high risk

Unlike Stages 1 and 2, this changes *when things are constructed*. Specific
hazards:

- **Import-time side effects.** `registerRules.ts` currently registers on
  import. Moving to `register(game)` means somebody must call it, and missing one
  produces a game with silently absent rules — no error, just wrong behaviour.
  Mitigate with a startup assertion: each package exports a rule count and `Game`
  verifies the total.
- **`AttributeRegistry`** has both a singleton and per-`Civilization` instances.
  Check every registry for this pattern before assuming it is global.
- **Order dependence.** Some rules may rely on registration order within a
  priority band. The conformance checksum catches this if it bites.

### Acceptance

- [ ] `new Game()` twice in one process; two independent games run 20 turns each
      with different seeds and neither affects the other's checksum
- [ ] Conformance suite constructs a fresh `Game` per test — no `beforeEach`
      reset needed
- [ ] Rule-count assertion passes for all 17 packages
- [ ] `web-renderer` still works via `defaultGame`

## Stage 4 — `transient` declarations

The state/derived split from [`02-design-review.md`](./02-design-review.md) §5,
and the mechanism from [`03-save-format.md`](./03-save-format.md).

### The change

`core-data-object` gains `static transient` and `allTransient()`. Then each of
the 24 stateful classes declares its exclusions:

```ts
export class Tile extends DataObject {
  static readonly transient = ['_ruleRegistry', '_yieldCache', '_neighbours'];
}

export class City extends DataObject {
  static readonly transient = ['_ruleRegistry', '_workedTileRegistry'];
}
```

Opt-out, not opt-in — the reasoning is in
[`03-save-format.md`](./03-save-format.md) and it matters: a new field is saved by
default, so the failure mode is wasted bytes rather than silent data loss.

### Also in this stage

- **Delete `PlayerTile._additionalData`** ([`01-constraints.md`](./01-constraints.md) §9).
  Write-only, retains cities and units per tile per player. Behaviour-neutral.
- **`PlayerWorld.entries()` returns a copy**, matching `World.entries()`.
- **Widen the conformance checksum** to cover all non-transient fields, and
  regenerate the fixtures.

### Acceptance

- [ ] Every class with private fields declares `transient` or provably needs none
- [ ] A test asserts every `transient` name exists on the class — a typo'd
      exclusion silently saves a registry and corrupts the file
- [ ] Widened checksum stable across runs
- [ ] `_additionalData` gone; conformance unchanged

## Stage 6 — Rule identity and `PendingEffect`

Independent of Stages 4 and 5; parallelisable.

### Rule identity

```ts
new Created(
  'civ1-city:city/created/register',
  new Criterion(/* … */),
  new Effect(/* … */)
)
```

`Rule`'s constructor already takes a variadic
`(Priority | Criterion | Effect)[]`; accept a leading `string`. Unnamed rules
keep working, so this lands package by package.

`RuleRegistry` then offers what plugins actually need:

```ts
game.rules.replace('civ1-city:city/created/register', myRule);
game.rules.disable('civ1-city:city/created/register');
game.rules.before('civ1-city:city/grow', myRule);
game.rules.after('civ1-city:city/grow', myRule);
```

`before`/`after` is the important half — it replaces the uncoordinated priority
numbers (`new Priority(9001)` with the comment *"just to make sure, it's over
9000"*) with ordering by reference.

Start with the packages a variant is most likely to override: `civ1-city`,
`civ1-unit`, `civ1-science`, `civ1-player`.

### `PendingEffect`

Convert Darwin's Voyage ([`01-constraints.md`](./01-constraints.md) §4) from a
closure-capturing runtime rule into a serialisable record, per
[`03-save-format.md`](./03-save-format.md).

Add a lint rule banning `ruleRegistry.register` inside an `Effect`, so the
pattern cannot silently return.

### Acceptance

- [ ] Named rules in the four `civ1-*` packages
- [ ] `replace`, `disable`, `before`, `after` tested
- [ ] Darwin's Voyage survives a save/load taken between building it and the next
      research — the specific bug this fixes
- [ ] Lint rule in place
- [ ] Stage 5's `pendingEffects` refusal removed

## Stage 7 — Registry indexes

Independent; parallelisable. Supersedes DEC-011's freeze on registry internals,
while leaving its ID-indexed export projections intact.

```ts
class UnitRegistry extends EntityRegistry<Unit> {
  #byPlayer = this.index((unit) => unit.player());
  #byTile = this.index((unit) => unit.tile());

  getByPlayer(player: Player): Unit[] { return this.#byPlayer.get(player) ?? []; }
}
```

Mutable keys are the catch — a unit's tile changes when it moves — so an indexed
field needs a reindex hook. `Unit.setTile` already exists and is the natural
place.

Also fix `PlayerWorld.get(x, y)` and `getByTile(tile)`
([`01-constraints.md`](./01-constraints.md) §9), which reimplement the linear
scan by hand and are called on every `unit:moved`.

### Acceptance

- [ ] `getByPlayer`, `getByTile`, `PlayerWorld.get`/`getByTile` are O(1)
- [ ] Reindex on `setTile`, city capture, unit destruction
- [ ] Conformance checksums unchanged
- [ ] A 150-turn headless run is measurably faster; record the numbers

```
Stage 0 ──► Stage 1 ──► Stage 2 ──► Stage 3 ──► Stage 4 ──► Stage 5

                          Stage 6 ──────────────────┤   (parallel from Stage 3)
                          Stage 7 ──────────────────┘   (parallel from Stage 1)
```

Stage 3 is the natural stopping point if effort runs out: Stages 0–3 deliver
determinism, test isolation and multiplayer-capable registries, all of which have
standalone value. Stages 4–5 without Stage 3 would give save/load for one game
per process, which is a dead end given multiplayer.

## Effort

Deliberately in publish waves and per-package touches rather than time, since
wave cadence dominates.

| Stage | Packages | Waves | Per-package work |
| ----- | -------: | ----: | ---------------- |
| 0 | 0 | — | Tooling and suite, up front |
| 1 | 62 | 12 | Minutes — codemod plus review |
| 2 | ~19 | 4 | Small — mechanical substitution |
| 3 | ~45 | 8 | **Moderate — needs judgement per package** |
| 4 | 24 | 7 | Small — one static declaration |
| 5 | 3 | 1 | Concentrated in one new package |
| 6 | ~20 | 5 | Moderate |
| 7 | ~8 | 3 | Small |

Stage 3 is where the real thinking is. Stage 1 is the largest by volume and the
smallest by difficulty, which is why it goes first — it proves the tooling while
every change is trivially reviewable.

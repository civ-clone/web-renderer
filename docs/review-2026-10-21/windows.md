# Review: windows, panels and actions (origin/main 18f28b0)


## Area health

The panels are small and readable. Their weakest point is how they learn that what they show has gone away. `DataObserver` matches ids against patch keys. Since #411, patches are keyed by the object that changed, so a panel that doesn't watch the player's id misses the "the city left your list" patch. The City screen is the main case. The other weak point is modal `<dialog>`s. `Window` prevents `cancel` and never listens for the dialog's native `close`, so Chromium's anti-abuse rule for Esc closes a modal behind the code's back and leaves it in the DOM. That rule closes a dialog without honouring `cancel` when there has been no user activation since the last Esc. This is the root cause of #351, and it also strands the Game Over window. Every literal i18n key resolves: 241 `t('…')` calls and every other key-shaped literal were checked against `translations/`. Two passed parameters don't match their strings, though, and i18next is initialised without `fallbackLng`, so any non-English browser sees raw keys everywhere. Options persistence (#343) is sound, and the request-based reports (Top Cities, Score, Intelligence, Hall of Fame) have no state to go stale.

## Already tracked

- **#351** (keys stop working; invisible NotificationWindow). Root cause reproduced in Chromium (`agent-windows/dialog-test.html`, which mirrors `Window`/`NotificationWindow`/`Notifications`):
  1. Esc on a `Notifications` modal runs `NotificationWindow.bindClose`, then `close()`. The `close` event goes to `Notifications.periodicChecker()`, which calls `check()` and `publish()`, so the next modal is created and `showModal()`ed synchronously, inside the same keydown.
  2. The keydown isn't `preventDefault()`ed, so Chromium then processes the Esc close request against the new top dialog. With no history-action activation (Esc doesn't grant one; the first Esc used it up) it closes that dialog without a cancelable `cancel`.
  3. The dialog stays connected with `.window.modal.notificationWindow`. `Notifications.check()` sees `.notificationWindow` and stops publishing, so notices pile up. `Renderer.ts:2006` forwards every key to that invisible `dialog.window.modal`, which acts only on Enter or Escape. Each Esc then releases one more window.

  So it happens from the second consecutive Esc dismissal, which matches "several notices arriving together". Fix: `preventDefault()` the Enter/Escape keydown in `NotificationWindow.bindClose`, and in `Window.bindClose` for Escape. Handle the native `close` event in `Window`. Have `Renderer` forward only to `dialog.window.modal[open]`.
- **#416** (notifications overflow; dismissing them): `Notices` and the `Actions` column behave as the issue describes. Nothing new.
- **#324**: two production pickers at once was fixed at the transport level. The UI can still open two (see findings).
- **#286**: units supported by a captured city aren't destroyed. That is also why the City screen's "city gone" close rarely fires.
- **#364** (accessibility): the Enter-closes-City-screen finding, the `<label>`s in `GameOptions` that aren't tied to their inputs, and the controls in `LockedSlider` that have no labels fall under it.
- **docs/known-issues-and-rewrite-notes.md**: "Trade-rate slider behavior can be inconsistent" (no issue). The `NaN`→50 finding is one concrete cause. The re-entrant `set()`→listener recursion in `LockedSliderGroup` is probably another.
- **#339** (UI never type-checked): the `!`s and casts here (`asset!.uri`, `this.#sliderGroup!`, `children.pop()!.querySelector('button')!`) would be flagged under it.

## Engine

- `@civ-clone/library-city/lib/assignWorkers.ts:68-91`: `changeSpecialist` replaces the `Specialist` with a new instance, so a new id, rather than changing its type in place. Any client that addresses specialists by id gets stale ids after every change (the cause of the specialist finding above).
- `@civ-clone/civ1-city/Rules/City/captured.ts:96-100` destroys the defender's units on the captured square, but not the units the city supported elsewhere (#286, tracked).

## Simplifications

- `CityStatus`, `TradeReport`, `HappinessReport` and `ScienceReport` each re-implement "observe the player and its cities, `setIds` from the new player, rebuild", and each fetches icon canvases and re-encodes them with `toDataURL` for every row on every update. A shared `observePlayerCities()` helper and a cached data-URL per icon would remove about 60 lines and repeated PNG encodes.
- `ChooseGovernment`, `ChooseResearch` and `CityBuildSelectionWindow` call `close()` inside `onChoose`, after `SelectionWindow.chooseHandler` has already closed the window. Each choice emits `close` twice.
- `City.#treasury` is written but never read. The gold treasury id is observed only until the first update (dropped by the `setIds` at 592), so drop both.
- `NotificationWindow`'s `notificationQueue`, `hasOpenWindow` and the `queue` option are dead (see findings). `TradeReport.ImprovementList.cost-value`/`surplus-value` are unused keys (the code formats all three totals with `income-value`).
- `ChooseResearch.ts:66`: `chosen: selection ? selection : '@'` is unreachable after the `if (!selection) return` above it.

- `tests/ui/window.ts` (new): the Escape (and, for `NotificationWindow`, Enter) keydown is `defaultPrevented`, and a natively closed modal (dispatch `close` with `open` false) is either removed or re-shown when `!canClose`. jsdom has no close watchers, so assert the handlers rather than the browser behaviour.
- `tests/ui/cityScreen.ts`: after a `patchdatareceived` keyed on the player id that drops the city from `data.player.cities`, plus `dataupdated`, the window is closed and its observer disposed.
- `tests/ui/cityScreen.ts`: Enter with a button focused doesn't close the screen. A specialist click sends the current specialist's id after a re-render.
- `tests/ui/unitSelectionWindow.ts` (new): clicking an awake unit calls `onComplete`, clicking an inactive one sends `InactiveUnit` and calls it, and the window closes either way.
- `tests/ui/translations.ts`: every literal `t('…')` key under `src/js/UI` exists (port `agent-windows/keys.js`). `Actions.CivilDisorder.title` renders the city with the args the button passes. i18next initialised with `lng: 'fr-FR'` still renders English.
- `tests/ui/notifications.ts` (new): `Notifications` publishes the next notice only after the previous window is removed, and `NotificationWindow` has no dead queue path.

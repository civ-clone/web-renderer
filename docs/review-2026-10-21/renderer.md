# Review: src/js/UI/Renderer.ts and src/js/UI/lib/ (origin/main 18f28b0)

## Area health

The core pieces in this area are in better shape than their size suggests. `IncrementalReconstituter` is fuzz-tested against `reconstituteData` as an oracle and handles the edge cases I tried: an id dropped and re-added, refs to ids the map doesn't hold yet (`#waiting`), aliases, `forget` after a prune, and an object that turns into an array. `PendingMove` with `drainKeys` drops or plays queued keys correctly in every path I traced. A change of active unit clears them, a refused move clears them, a window opening clears them, and a `turnEnded` that swallows an unacknowledged move clears them through `activate(null)`. Every new game and every load goes through `location.reload()`, so the listeners `init()` registers for each game and never removes cannot pile up. The weak spot is the `document` keydown handler at Renderer.ts:1997. It ignores Ctrl, Cmd and Alt entirely, so browser shortcuts become unit orders and map toggles. Two smaller ordering problems cause stale or slow updates: one leaves observed windows stale during the AI turns, and the other is an O(objects) `Object.keys` on every patch. The rest of `Renderer.ts` is hard to test because it all lives in one closure. Every test of it (activeUnit.ts, incrementalReconstitute.ts) re-implements its logic rather than importing it, and the copies have already begun to drift. I checked every i18n key in the area. All the literal keys exist in `translations/*/en.ts`. Of the dynamic ones, `JoinCity.${reason}` covers the only reason the engine sends, and `ChooseFromList.${key}.random` exists for `choose-civilization`, the only key that uses it.

## Already tracked

- **#351** (keys stop working behind an invisible NotificationWindow). Two mechanisms in this area fit it:
  - The forwarding at Renderer.ts:2006 and the check at :1510 use `document.querySelector('dialog.window.modal')`, which finds the **oldest** modal in document order, not the topmost one. With two modal notifications stacked, Enter or Esc pressed while focus is on body closes the one underneath, which the player can't see.
  - `NotificationWindow.hasOpenWindow()` (components/NotificationWindow.ts:12) selects `div.notificationWindow`, but windows are `<dialog>` elements, so it never matches. The queue never engages, and every notification opens at once, stacked.
- **#274**: rules encoded in the UI. The welcome window hardcodes `'Irrigation', 'Mining', 'Roads'` (Renderer.ts:668), untranslated, and the JoinCity icon shows `size + 1` (unitActionIcon.ts:64).
- **#339**: `t()` typing and the UI type errors in general.
- **#344**: `Renderer.ts`, the one `init()` closure, and the `dataupdated`/`patchdatareceived` events.
- **#358**: the resize handler (Renderer.ts:774) only reacts to a change in the canvas's pixel size, not to a change in devicePixelRatio.
- **#416**: late-game notifications overflow and block auto end turn.
- **#68**: `remove` patches. The Renderer still handles them, and any `remove` would make `IncrementalReconstituter` refill everything (`refillAll`), but `DataTransferClient` never calls `DataQueue.remove`.
- **#151**: turn hand-over refinements, buffering input.

## Engine

- Nothing wrong found in the parts of node_modules/@civ-clone/* I read: civ1-unit/AdditionalData/joinCityRefusal.ts, core-turn-based-game/Events/Engine/start.ts, civ1-player/Rules/Player/Action.ts and base-player-action-active-unit. `joinCityRefusal` only ever sends `reason: 'too-large'`, which has its translation.
- Outside node_modules, for whoever has src/js/Engine: in `DataTransferClient.takeTurn` the `action` listener is async and `EventEmitter` doesn't serialise it. An action that arrives while another is still awaiting `#talks` or `talkToPlayersMet` runs concurrently with it, and the second one to finish resets `#holdingFlushes` while the first is still running. The UI holds keys only behind plain moves (`PendingMove`), so a key repeated after an attack, or after a terraform order, can trigger this. PLAUSIBLE; not traced in full.

## Simplifications

1. Move the `gameDataPatch` application (`pathToParts`, `setObjectPath`, `removeObjectPath` and the add/update/remove loop) into `lib/`. tests/ui/incrementalReconstitute.ts:117-160 currently keeps its own copy.
2. Move `playUnitKey`, `drainKeys` and the keydown routing into a `lib/` input module. tests/ui/activeUnit.ts:359+ re-implements them, and the copy already differs: it chooses a key's action in the unit's action order, where the Renderer uses the order of `keyToActionsMap[key]`.
3. Delete `src/js/UI/lib/augmentData.ts` and `instanceOfAll` (lib/instanceOf.ts:21). Nothing imports either.
4. Remove the dead persistent `gameData` receiver (Renderer.ts:1740).
5. Replace the three `Object.keys(objectMap.objects).length` recounts with one counter that the patch handler maintains.

## Coverage gaps

- tests/ui (new, e.g. `rendererKeys.ts`, after simplification 2): Ctrl/Cmd/Alt combinations (`Ctrl+R`, `Cmd+F`, `Ctrl+S`) send no unit action and don't toggle layers, and Caps Lock `P` doesn't pillage.
- tests/ui/activeUnit.ts: a waiting-for-turn sequence (state update, then render, then a patch, then a state update) in which an observer flagged by the later patch receives the updated `data`.
- tests/ui/translations.ts: `JoinCity.too-large.body` for a city whose name contains an apostrophe or `&`, displayed as text.
- tests/ui (keys): Shift+5, Shift released and pressed again, Shift+6 still enables cheats.
- tests/ui/incrementalReconstitute.ts: already covers the reconstituter's edge cases well. Once simplification 1 is done, it should run the real patch handler.
